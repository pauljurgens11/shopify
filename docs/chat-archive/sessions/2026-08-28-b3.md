## What shipped

`/admin/api/collections` CRUD + `/:id/products` (read & mutate membership), all behind `requirePermission('products')`. Routes are thin; every rule lives in [collections.ts](apps/api/src/services/catalog/collections.ts) so E1/H1 can call it without HTTP.

The core design decision: **a smart collection is a `where` clause, not a materialized list.** Rules translate to Prisma filters resolved on read — no republishing job, nothing to go stale, and a 24-product page is one indexed query. `productCount` is derived the same way.

Three judgment calls worth flagging (all in `DECISIONS.md`):

- **Unsupported `(column, relation)` pairs are a 400, not a dropped clause.** `tag contains "sal"` has no array-substring operator in Postgres; silently ignoring it would publish a collection that quietly means something else. Same for a price condition typed as `"20.00"` — conditions are integer minor units, and a decimal must not reach a where clause as `NaN`.
- **`inventory_quantity` compares stock at a single location**, not summed across locations — an aggregate over a relation isn't expressible as a Prisma filter, and per-location is the number the merchant reads in the inventory table.
- **Member pages use an opaque *offset* cursor**, unlike the id cursor on the products index: the sort key can be a related aggregate (cheapest variant, units sold) that no row id anchors. SPEC §5 fixes the `?cursor=` shape, not its contents.

## Testing

23 tests against real Postgres, written before the implementation (they caught a real bug on the first run — Prisma rejects the FK inside a nested `createMany`). One case per supported rule pair, the refused ones, any/all disjunction, NULL handling on negated text rules (`"vendor is not Northwind"` must include a product with no vendor — SQL's `<>` doesn't), manual reorder persistence, every sort order, and two cross-tenant cases.

`pnpm verify` green. I also ran it over real HTTP against H1's newly-landed Aurora Supply Co. seed — all four demo collections resolve correctly, including `new-arrivals` (smart, `tag equals new` → 5 products) and `everyday-basics` (manual members, title-asc).

## Answer to your question

Yes — **B2 and B3 could both run in parallel** with B4. B1 and A1 (their only dependencies) were already merged, and the three own disjoint paths. I took **B3** because it unblocks more downstream work (B6, E1 storefront collections, F1's `featured-collection` section). **B2 (files/media, MinIO presign) is still unclaimed** and I flagged that in `docs/AGENT-LOG.md` for whoever picks up next.

## What landed

`/admin/api/collections` CRUD plus `/:id/products` for reading and mutating membership, all behind `requirePermission('products')`. Routes are thin; the logic lives in [collections.ts](apps/api/src/services/catalog/collections.ts) so E1 and H1 can call it without HTTP.

The core decision: **a smart collection is a `where` clause, not a materialized list.** Rules translate to Prisma filters resolved on read — no republishing job, nothing to go stale, a 24-product page is one indexed query. `productCount` is derived the same way.

Three judgment calls, all logged in `DECISIONS.md`:

- **Unsupported `(column, relation)` pairs are a 400, not a dropped clause.** `tag contains "sal"` has no array-substring operator in Postgres; ignoring it would publish a collection that quietly means something else. Same for a price condition typed `"20.00"` — conditions are integer minor units, and a decimal must not reach a where clause as `NaN`.
- **`inventory_quantity` compares stock at a single location**, not summed across locations — a relation aggregate isn't expressible as a Prisma filter, and per-location is the number the merchant sees in the inventory table.
- **Member pages use an opaque *offset* cursor**, unlike the id cursor on the products index: the sort key can be a related aggregate (cheapest variant, units sold) that no row id anchors.

## Testing

23 tests against real Postgres, written before the implementation — they caught a real bug on first run (Prisma rejects the FK inside a nested `createMany`). One case per supported rule pair, the refused ones, any/all disjunction, NULL handling on negated text rules (`"vendor is not Northwind"` must include a product with no vendor; SQL's `<>` doesn't), manual reorder persistence, every sort order, two cross-tenant cases. A self-review before pushing found two gaps I then closed: the manual-membership `where` had no coverage, and an absurd decoded offset would have 500'd instead of 400'ing.

`pnpm verify` green, and I exercised it over real HTTP against H1's Aurora Supply Co. seed — all four demo collections resolve correctly.
