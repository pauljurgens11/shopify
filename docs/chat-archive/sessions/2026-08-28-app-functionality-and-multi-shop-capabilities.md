## Your specific question

**Multiple shops — yes.** Sign up repeatedly; each gets its own slug, its own subdomain storefront, its own isolated data. The same email can own several stores, and login disambiguates with a store slug ([auth/index.ts:176](apps/api/src/routes/auth/index.ts:176)).

**Custom products — yes.** A new shop starts with *zero* products (the seed data is only for the `demo` shop), so you add your own through Products → Add product, with images.

**"AI created" — partially.** The AI builds the **storefront design**, not the store. It takes a prompt ("make it feel like a Kyoto coffee shop") plus your real product/collection handles and returns a validated theme document — palette, typography, section layout ([ai-theme-generate.ts](apps/worker/src/jobs/ai-theme-generate.ts)). It will not invent products or write your catalog for you. So the order is: create shop → add your products → let the AI design the storefront around them.

**Profits — no.** Two hard limits:

1. **The money is simulated.** The default processor is a mock/simulated adapter with test cards. The Stripe adapter is real code but is only live if *you* paste your own keys, and Stripe gates raw PANs behind PCI enablement, so a stock account will decline ([stripe.ts:12](packages/pay/src/adapters/stripe.ts:12)). Nothing settles to a bank.
2. **There is no profit model.** No `costPerItem`, no margin, no COGS anywhere in the schema or contracts — I grepped. Analytics reports gross sales, AOV, sessions, conversion. Revenue, not profit.

Also, there's no deployment yet — `A5` is the unbuilt issue that would make this reachable outside `localhost`. Today it runs on your machine via `pnpm dev`.

So: a genuinely convincing multi-store Shopify clone you can drive end to end, with AI-designed storefronts and your own catalog. A demo economy, not a real one.

### 🤖 Claude

Understood — not doing it, just answering.

**Yes, buys show up in analytics — with a caveat about *where* and *when*.**

Two different surfaces:

- **Orders → immediate.** The orders index, order detail, customer's order history, product inventory: all read live tables. A checkout completes, it's there on refresh.
- **Analytics dashboard → rolled up, not live.** It reads `AnalyticsRollupDaily`, written by a repeatable worker job that runs **every 5 minutes** and re-aggregates today and yesterday ([analytics-rollup.ts](apps/worker/src/jobs/analytics-rollup.ts)). So a sale appears on the dashboard within ~5 minutes, provided `pnpm dev` is running the worker. It's not instant, and it's not broken if it isn't there yet.

**What feeds which metric matters for a realistic-looking demo:**

- `sales` and `orders` come from **Order rows** (cancelled ones excluded — a cancellation removes revenue it never earned).
- `sessions`, `product_views`, `add_to_carts`, `begin_checkouts`, `purchases` come from **AnalyticsEvent rows**, which the *storefront* emits as someone browses.

That split is the thing to know: if sales were injected straight into the database, you'd get a revenue line with a dead funnel above it — 0 sessions, 0 conversions. Convincing simulation has to walk the storefront, not just write orders.

**On simulating it — yes, very doable, two ways:**

1. **Real checkouts.** Drive the storefront in a browser: browse products, add to cart, check out with the simulated processor's test cards. Generates genuine events *and* orders, so the whole funnel is coherent. Slow per-order, best for a handful.
2. **A seeding script.** There's already precedent — `packages/db/prisma/seed/analytics.ts` writes the demo shop's closed-day history, and the rollup job's comments say the two must agree metric-for-metric. A script could fabricate orders + matching events across the past 30 days and call `rollupDay()` per day. Note the repeatable job only touches today and yesterday, so **backdated days need an explicit rollup call** — otherwise the chart stays flat before today.

Worth knowing: a brand-new shop you sign up starts with a **completely empty dashboard**. The rich history is seeded for the `demo` shop only.

Say the word when you want it and I'll build the simulator — probably option 2 with option 1 for the last day or two, so the recent numbers are real.

1. `POST /storefront/api/events` — beacon a `product_view`, `add_to_cart`, `begin_checkout`, each under its own fresh `sessionId` so it reads as seven different visitors

Two details that make this work properly:

- **The purchase metric is handled for you.** The events endpoint deliberately *drops* client-sent `purchase` events — anyone could curl revenue into a dashboard otherwise — and writes the authoritative one server-side at order creation. So the funnel stays honest by construction.
- **Nothing is faked.** These are the same calls the storefront makes, so the orders show in Orders, the customer shows in Customers, inventory drops, the webhook fires, and analytics rolls up within ~5 minutes.
