## What shipped

**[crypto.ts](packages/pay/src/crypto.ts)** — AES-256-GCM under the single `VAULT_MASTER_KEY`, 96-bit IV, no rotation machinery (SPEC §11 says so explicitly). Decrypt failures rethrow a generic message so plaintext can never ride out on an exception.

**[vault.ts](packages/pay/src/vault.ts)** — Luhn, IIN brand detection (the 2-series Mastercard 2221–2720 and JCB 3528–3589 ranges are the ones a naive first-digit check gets wrong), expiry, seal/open, `tokenizeCard`, and `getCard` — marked loudly as pay-internal because it's the one function that decrypts.

**[POST /vault/tokenize](apps/api/src/routes/vault/tokenize.ts)** — unauthenticated by design and resolved from the `Origin` subdomain, since at that point in checkout there's no session, only a storefront origin; bounded by `RATE_LIMITS.checkoutPayment`. Validation errors carry `field` so E4 renders them inline. Formatted card numbers (`4242 4242 4242 4242`) normalize before the contract's digits-only check.

## Tests — 60, written before the code

The mandated §14.2 set, plus what the vault specifically must never do: PAN absent from the sealed blob (base64 *and* decoded bytes), absent from every validation message, absent from `validateCard`'s return type entirely. Tamper cases for ciphertext, IV, and authTag independently.

## Two platform bugs found and fixed

1. `app.ts` gave `@fastify/rate-limit` a plain object as its error body — but the plugin **throws** that value, and with no `statusCode` it fell through the error handler as a **500 instead of a 429**. It now returns an `ApiError`. My route was the first to use route-level rate limiting, so nothing had hit it. Flagged to WS-A in the log rather than silently kept.
2. `pr-checks.yml` had `VAULT_MASTER_KEY` unquoted — YAML reads 64 zeros as the number `0`, so **CI was running with `VAULT_MASTER_KEY="0"`**. Invisible until a test read the variable. This one cost a red CI run before I diagnosed it.

Three `DECISIONS.md` lines cover the resolved ambiguities — notably that tenant writes must still pass `shopId` in `data` for Prisma's types even under `dbForShop` (the extension overrides it), which every B/C/E agent will hit on their first write.
