2026-08-28 | WS-A | Internal packages export TypeScript source (`exports: "./*": "./src/*.ts"`) with no build step — removes cross-package build ordering, which is the most common way a parallel-agent monorepo deadlocks.
2026-08-28 | WS-A | Prisma multi-file schema (`prisma/schema/*.prisma`, one file per domain) instead of a single `schema.prisma` — a single schema file would be the single hottest merge conflict in the repo.
2026-08-28 | WS-A | `@node-rs/argon2` instead of `argon2` — prebuilt binaries, so no node-gyp toolchain in CI or in agent sandboxes. Same argon2id algorithm, satisfies SPEC §8.
2026-08-28 | WS-A | `packages/contracts` has no barrel `index.ts`; consumers import subpaths (`@merchant/contracts/products`) — a shared barrel is a guaranteed conflict point and hurts tree-shaking.
2026-08-28 | WS-A | Admin navigation, theme sections, and worker job registries are pre-created complete from SPEC §9/§12/§13 — agents fill leaf files instead of editing a shared registry array.
2026-08-28 | WS-A | PR-required CI is limited to lint + typecheck + unit + tenancy (fast); Playwright e2e and docker build run post-merge on `main` — required checks that take 10 min would serialize 20 agents behind the merge queue.
2026-08-28 | WS-A | React 19 with Polaris 13 despite its `react@^18` peer range — verified the 13.9.5 build uses no findDOMNode, defaultProps, or propTypes (the three things React 19 removed). SPEC §3 locks both Polaris 13 and Next 15, and Next 15 App Router requires React 19, so the peer range is stale rather than a real conflict. Allowed explicitly via pnpm.peerDependencyRules.
2026-08-28 | WS-A | Root `.env` is loaded explicitly per app — `--env-file` for api/worker, `process.loadEnvFile()` in next.config for admin/storefront. Next only reads `.env` from its own directory, so a single root `.env` (SPEC §5) is otherwise invisible to it.
2026-08-28 | WS-A | Admin pages are Client Components; Polaris needs React context and breaks the build inside a Server Component. Verified: admin and storefront both build clean on Next 15.5 + React 19.
2026-08-28 | WS-A | Postgres is published on host port 5433, not 5432 — a stock Postgres or another project's container commonly already owns 5432, and the resulting bind error is a confusing first-run failure. Container port is unchanged.
2026-08-28 | WS-A | Prisma generates to its DEFAULT output, not a custom dir — a custom path is imported relatively, so bundlers inline the CJS client and its dynamic require("fs") throws under ESM. As `@prisma/client` it stays external everywhere.
2026-08-28 | WS-A | api and worker run from TypeScript source under tsx in production; no bundler. @fastify/autoload discovers routes by scanning the filesystem, so a single-file bundle has no route tree, and bundling also inlines Prisma/argon2 and breaks them. Costs ~1s startup compile; buys prod behaviour identical to dev. Verified by running both in NODE_ENV=production.
2026-08-28 | WS-A | Next apps build with `output: 'standalone'` + `outputFileTracingRoot` at the workspace root — pnpm's symlinked node_modules does not survive a cross-stage Docker COPY, and without the tracing root standalone silently omits workspace packages.
2026-08-28 | ROOT | Development plan lives as parallel-safe issue files in docs/issues/ (README = protocol, INDEX = grab list) — agents claim via docs/AGENT-LOG.md, one issue = one PR, tests named per issue land with the feature.

2026-08-28 | WS-A | Autoload maps routes/admin→/admin/api and routes/storefront→/storefront/api via dirNameRoutePrefix — on-disk layout in WORKSTREAMS.md stays, URLs land on SPEC §5/§10 paths.
2026-08-28 | WS-A | dbForShop deep-stamps nested create/createMany/connectOrCreate via Prisma DMMF relation metadata, scopes Shop reads to id=shopId, scopes OrderSequence, memoizes clients per shop — nested connect and $queryRaw remain review-covered (see tenant.ts header).
2026-08-28 | WS-A | Session cookie NAME is constants.SESSION_COOKIE only; SESSION_COOKIE_NAME env var removed — one source of truth before auth lands.
2026-08-28 | WS-A | fromDecimal parses decimal strings digit-wise (BigInt), never via float multiply — Math.round(1.005*100)===100 was a live off-by-one-cent bug.
2026-08-28 | WSC | Engine `discountTotal` covers line discounts only and `shippingTotal` is already net of `shippingDiscount` — callers compute `subtotal - discountTotal + shippingTotal + tax`; folding free shipping into `discountTotal` (as C1's parenthetical suggested) double-counts it in checkout totals and does not match how Shopify shows shipping as "Free".
2026-08-28 | WSC | Discounts apply in the order products → order → shipping, each taking its percentage off what the previous ones left on the line — two stacked 10% automatics take 19%, not 20%.
2026-08-28 | WSC | `amount_off_products` with a `fixed` value is one pool taken off the eligible lines and split with `allocate`, not "$X off each item" — same code path as `amount_off_order`, so cents balance identically for both.
2026-08-28 | WSC | Only the code the shopper actually typed can be rejected; any other code-bearing row the caller passes is ignored silently — a rejection the shopper never triggered would render as a bogus checkout error.
2026-08-28 | WSC | Discount date window is authoritative and the denormalized `status` column only vetoes via `disabled` — a scheduled discount whose start time has passed is live without waiting for a job to update the row.
2026-08-28 | WSC | Minimum subtotal/quantity requirements are measured over the discount's own eligible lines, pre-discount, and a non-empty cart matching no eligible line rejects as `minimum_not_met` (Shopify's "not valid for the items in your cart").
2026-08-28 | WS-D | Vault ciphertext/iv/authTag stay in the three VaultCard columns rather than one packed base64 string (D1 wording) — the schema already has the columns, and ProcessorConfig mirrors them for credentials.
2026-08-28 | WS-D | `tokenizeCard(db, shopId, card)` takes shopId even though `dbForShop` stamps it: Prisma's generated create input still requires the column at the type level, so every tenant write must pass it (the extension overrides whatever is passed). Reads do not — `getCard(db, cardTokenId)` is scoped by the client alone.
2026-08-28 | WS-D | /vault/tokenize resolves its shop from the request Origin subdomain and is unauthenticated by design (SPEC §11) — at that point in checkout there is no session, only a storefront origin; abuse is bounded by RATE_LIMITS.checkoutPayment.
2026-08-28 | WSF | `renderSection(section, data)` takes a `SectionDataContext` — core sections need live product/collection/cart data, and interactivity arrives as slots WS-E owns (Server Components have no state). 2026-08-28 | WSF | Button appearance is derived at token time (`--theme-button-bg/-fg/-border` in `themeCssVariables`), not inside `ThemeButton` — CSS cannot branch on the *value* of a custom property, and a Server Component section has no access to tokens.
2026-08-28 | WSF | Presets are authored as zod *input* and parsed on every `presetThemeDoc()` call — fills every schema default, makes an invalid preset a CI failure rather than a broken storefront, and hands each caller an independent object to mutate.
2026-08-28 | WSF | The storefront cart CTA targets `/checkout` (Shopify's own path); WS-E creates the checkout there and redirects to WS-E4's `/checkouts/{token}`. Sections never build checkout URLs themselves — `shared/urls.ts` is the one place routes are written.
2026-08-28 | WS-D | `ProcessorAdapter` takes `creds` per call rather than binding them at construction (pre-existing, logged now per issue D2) — routing is per-merchant, so one process serves many shops' credentials; a per-shop adapter instance means a per-shop SDK client cache and a place for one tenant's key to serve another.

2026-08-28 | WS-D | The `…0119` outage card hard-fails on `mock` but APPROVES in `maverick` simulated mode — a router failover is only demonstrable end-to-end if the second processor is healthy for the same card. Deliberate asymmetry, not a bug.
2026-08-28 | WS-D | `maverick.verifyCredentials({})` returns true — simulated mode is a working mode that the demo routes real checkouts through, so it reports connected. `maverickMode(creds)` is the live/simulated discriminator for the D4 settings badge, and every simulated approval carries `raw.simulated === true`.
2026-08-28 | WS-D | Stripe `StripeInvalidRequestError`/`StripeIdempotencyError` map to `declined`+`processing_error`, not `hard_failure` — the contract's `hard_failure` is `retryable: true` by construction, and failing over on our own bad request either repeats the bug or double-charges.
